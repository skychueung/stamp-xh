# STAMP v0.11 Experimental Validation Data Model Design

**Version**: v0.11-P1  
**Date**: 2026-05-10  
**Author**: KimiCode  
**Branch**: `v0.11-wetlab-validation`

---

## 1. Why v0.11?

v0.10 completed the **computational closed loop**:

```
Target protein → BepiPred3 → PepMLM-650M → LocalColabFold → pDockQ → FoldX → Report export
```

All outputs in v0.10 are explicitly `NOT_EXPERIMENTALLY_VALIDATED`.

v0.11 transitions from the **computational loop** to the **wet-lab validation loop**:

```
Computational candidate → Wet-lab assay planning → Assay execution → Measurement recording
→ Validation status update → Candidate prioritization → Experiment report
```

This design document defines the data model, status state machine, and priority scoring rules.

## 2. Data Model

### 2.1 experimental_validation_runs

A run represents a single experimental assay plan or execution for one candidate.

| Column | Type | Description |
|--------|------|-------------|
| `id` | UUID string | Primary key |
| `project_id` | FK → projects.id | Project scope |
| `candidate_id` | FK → stamp_candidates.id | Candidate scope |
| `experiment_type` | String(50) | `MIC`, `MBC`, `HEMOLYSIS`, `CYTOTOXICITY`, `SERUM_STABILITY`, `PROTEASE_STABILITY`, `SALT_STABILITY`, `BIOFILM`, `RESISTANCE_INDUCTION`, `OTHER` |
| `organism` | String(100) | Test organism (e.g., *S. aureus*) |
| `strain` | String(100) | Specific strain |
| `protocol_name` | String(255) | Protocol reference |
| `protocol_version` | String(50) | Protocol version |
| `operator` | String(100) | Lab operator |
| `experiment_date` | DateTime | Date of execution |
| `status` | String(20) | `PLANNED`, `RUNNING`, `COMPLETED`, `FAILED`, `INVALIDATED` |
| `validation_status` | String(50) | Computed by service layer |
| `notes` | Text | Free-text notes |
| `created_at`, `updated_at` | DateTime | Timestamps |

### 2.2 experimental_measurements

A measurement is a single numerical result from a run.

| Column | Type | Description |
|--------|------|-------------|
| `id` | UUID string | Primary key |
| `validation_run_id` | FK → experimental_validation_runs.id | Parent run |
| `candidate_id` | FK → stamp_candidates.id | Candidate scope |
| `metric_name` | String(50) | `MIC_ug_ml`, `MBC_ug_ml`, `hemolysis_percent`, `HC50_ug_ml`, `IC50_ug_ml`, `cell_viability_percent`, `serum_half_life_min`, `protease_remaining_percent`, `biofilm_inhibition_percent` |
| `value` | Float | Numeric result |
| `unit` | String(20) | Unit (e.g., `ug/ml`, `%`, `min`) |
| `condition_json` | JSON | Medium, temperature, incubation time, inoculum, cell type, species, replicate |
| `replicate_id` | String(20) | Replicate identifier |
| `raw_data_path` | String(500) | Path to raw data file |
| `quality_flag` | String(20) | `PASS`, `WARNING`, `FAILED`, `NEEDS_REVIEW` |
| `created_at`, `updated_at` | DateTime | Timestamps |

## 3. validation_status State Machine

The `validation_status` on `stamp_candidates` is **computed by the service layer**, not directly set by users.

```
                    ┌─────────────────────────────────────┐
                    │  NOT_EXPERIMENTALLY_VALIDATED       │
                    │  (default, no runs exist)           │
                    └──────────────┬──────────────────────┘
                                   │ create run
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  EXPERIMENT_PLANNED                 │
                    │  (run created, status=PLANNED)      │
                    └──────────────┬──────────────────────┘
                                   │ add measurements,
                                   │ mark COMPLETED
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  PARTIALLY_VALIDATED                │
                    │  (completed runs + measurements,    │
                    │   but missing full activity+safety) │
                    └──────────────┬──────────────────────┘
                                   │ add remaining metrics
                                   │ (activity + safety, all PASS)
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  EXPERIMENTALLY_VALIDATED           │
                    │  (full activity + safety, all PASS) │
                    └──────────────┬──────────────────────┘
                                   │ any measurement FAILED
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  VALIDATION_FAILED                  │
                    │  (critical assay failed)            │
                    └─────────────────────────────────────┘
```

### State Rules

| Condition | validation_status |
|-----------|-------------------|
| No runs | `NOT_EXPERIMENTALLY_VALIDATED` |
| Only `PLANNED` runs | `EXPERIMENT_PLANNED` |
| Any run `FAILED` | `VALIDATION_FAILED` |
| Any measurement `quality_flag=FAILED` | `VALIDATION_FAILED` |
| `COMPLETED` + measurements, but incomplete set | `PARTIALLY_VALIDATED` |
| `COMPLETED` + activity + safety + all `PASS` | `EXPERIMENTALLY_VALIDATED` |

## 4. Field Definitions

### 4.1 Antimicrobial Activity

| Metric | Unit | Interpretation |
|--------|------|----------------|
| `MIC_ug_ml` | ug/ml | Minimum inhibitory concentration. Lower = more potent. |
| `MBC_ug_ml` | ug/ml | Minimum bactericidal concentration. Lower = more potent. |

### 4.2 Safety

| Metric | Unit | Interpretation |
|--------|------|----------------|
| `hemolysis_percent` | % | Red blood cell lysis. Lower = safer. |
| `HC50_ug_ml` | ug/ml | Concentration causing 50% hemolysis. Higher = safer. |
| `IC50_ug_ml` | ug/ml | Concentration inhibiting 50% cell growth. Higher = safer. |
| `cell_viability_percent` | % | Cell survival. Higher = safer. |

### 4.3 Stability

| Metric | Unit | Interpretation |
|--------|------|----------------|
| `serum_half_life_min` | min | Time to 50% degradation in serum. Higher = more stable. |
| `protease_remaining_percent` | % | Remaining peptide after protease treatment. Higher = more stable. |

## 5. Candidate Priority Scoring

### 5.1 When No Experimental Data

```
experimental_priority_score = None
priority_status = "PENDING_EXPERIMENTAL_DATA"
```

### 5.2 When Experimental Data Exists

```
experimental_priority_score =
    computational_score_contribution     (composite_score normalized × 0.40)
  + structure_support_contribution       (structure/interface/energy quality × 0.20)
  + experimental_activity_contribution   (MIC/MBC normalized × 0.25)
  + safety_contribution                  (hemolysis/cytotoxicity normalized × 0.15)
```

| Component | Weight | Source |
|-----------|--------|--------|
| Computational | 40% | `composite_score` from v0.10 (normalized 0–1) |
| Structure Support | 20% | mean pLDDT, pDockQ, FoldX interaction_energy |
| Experimental Activity | 25% | MIC/MBC (lower = better, normalized via sigmoid) |
| Safety | 15% | hemolysis %, cell viability %, HC50 |

### 5.3 priority_status Values

| Status | Condition |
|--------|-----------|
| `PENDING_EXPERIMENTAL_DATA` | No experimental measurements |
| `READY_FOR_PRIORITIZATION` | `EXPERIMENTALLY_VALIDATED` |
| `PARTIALLY_PRIORITIZED` | `PARTIALLY_VALIDATED` |
| `FAILED_SAFETY_OR_ACTIVITY` | `VALIDATION_FAILED` |

## 6. Boundary with v0.10 Computational Metrics

### What v0.10 Provides (Immutable)
- `composite_score` — computational ranking score
- `structure_prediction` — ColabFold pLDDT/pTM/ipTM
- `interface_quality` — pDockQ
- `energy_quality` — FoldX interaction_energy

### What v0.11 Adds (New)
- `experimental_validation_runs` — wet-lab assay tracking
- `experimental_measurements` — assay numerical results
- `validation_status` — computed from real data
- `experimental_priority_score` — hybrid computational + experimental score

### What NEVER Happens
- ❌ Computational modules do NOT auto-generate experimental data
- ❌ No `MIC_ug_ml` is fabricated from `composite_score`
- ❌ No `hemolysis_percent` is estimated from `pDockQ`
- ❌ `validation_status` is NOT set to `EXPERIMENTALLY_VALIDATED` without real measurements

---

## 7. No Fabricated Data Principle

1. **All experimental data must be entered by a user or imported from a lab file.**
2. **Default `validation_status` is `NOT_EXPERIMENTALLY_VALIDATED`.**
3. **Only the service layer can promote `validation_status` based on measurement rules.**
4. **When no data exists, reports explicitly state: "No wet-lab measurements have been recorded."**
5. **When data exists, reports clearly label it as `EXPERIMENTAL` and separate it from `COMPUTATIONAL` sections.**
