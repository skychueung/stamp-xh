# STAMP v1.2-lab-production Implementation Phases

**Version:** 1.2-lab-production  
**Date:** 2026-05-12  
**Branch:** `v1.2-lab-production`

---

## Overview

This document breaks the v1.2 roadmap into concrete, sequenced phases. Each phase has:
- Clear deliverables
- Entry/exit criteria
- Files to create/modify
- Test requirements
- Scientific boundary checks

No long-running compute is started during any phase. Production MD (P7) is prepared, configured, and guarded — but actual 10–50 ns simulations are scheduled outside these development sprints.

## P1: Real Backend Job Queue

**Duration:** 1 week  
**Goal:** Replace mock/async stubs with a real job queue system.

### Deliverables
1. Queue adapter abstraction (`app/services/job_queue_adapter.py`)
2. RQ-based implementation (`app/services/job_queue_rq.py`)
3. Worker entrypoint (`backend/worker.py`)
4. `ComputeJob` SQLAlchemy model + Alembic migration (or auto-create for SQLite)
5. Job status API endpoints:
   - `POST /api/v1/jobs` — submit job
   - `GET /api/v1/jobs/{job_id}` — get status
   - `POST /api/v1/jobs/{job_id}/cancel` — cancel
   - `POST /api/v1/jobs/{job_id}/retry` — retry
6. Retry fields: `retry_count`, `max_retries`, `error_json`
7. Tests: `backend/tests/test_job_queue.py`

### Exit Criteria
- [ ] A job can be enqueued, run by a worker, and status polled end-to-end.
- [ ] Retry logic works for simulated failures.
- [ ] No existing tests broken.

### Files
- New: `backend/app/services/job_queue_adapter.py`
- New: `backend/app/services/job_queue_rq.py`
- New: `backend/worker.py`
- New: `backend/app/models/compute_job.py`
- New: `backend/tests/test_job_queue.py`
- Mod: `backend/app/database.py` (add model)
- Mod: `backend/requirements.txt` (add `redis`, `rq`)

## P2: Multi-Candidate Batch Jobs + Server Scheduler

**Duration:** 1–1.5 weeks  
**Goal:** Run compute on many candidates as a batch; schedule heavy jobs to the lab server.

### Deliverables
1. `ComputeBatch` model + API
2. Batch submission endpoint:
   - `POST /api/v1/batches` — submit batch with candidate_ids and pipeline stages
3. Batch status endpoint:
   - `GET /api/v1/batches/{batch_id}` — summary + per-candidate job statuses
4. Batch retry-failed endpoint:
   - `POST /api/v1/batches/{batch_id}/retry-failed`
5. Server scheduler config (`app/config/server_scheduler.py`)
6. Server environment checker (`app/services/server_env_checker.py`)
7. SSH runner wrapper (`app/services/server_runner.py`)
8. Tests: `backend/tests/test_batch_jobs.py`, `backend/tests/test_server_scheduler.py`

### Exit Criteria
- [ ] A batch of 3 candidates can be submitted and tracked.
- [ ] Server env checker reports missing envs correctly.
- [ ] Jobs are marked with `server_host = "192.168.31.218"` for heavy compute.
- [ ] No existing tests broken.

### Scientific Boundaries
- [ ] No MD or MM-GBSA actually launched (only job metadata created).
- [ ] `official_mm_gbsa_delta_g` cannot be set via batch API.

## P3: Batch Compute Management

**Duration:** 1.5–2 weeks  
**Goal:** Standardized wrappers for ColabFold, FoldX, FlexPepDock, and MM-GBSA readiness.

### Deliverables
1. `ColabFoldBatchWrapper`
   - Input: candidate sequences
   - Output: predicted PDB + pLDDT JSON
   - Job type: `colabfold_structure_prediction`
2. `FoldXBatchWrapper`
   - Input: PDB + candidate sequence
   - Output: interaction energy + energy terms JSON
   - Job type: `foldx_energy_quality`
3. `FlexPepDockBatchWrapper`
   - Input: receptor PDB + peptide sequence
   - Output: docked poses + scores
   - Job type: `flexpepdock_refinement`
4. `MmgbsaReadinessWrapper`
   - Input: topology + trajectory
   - Output: readiness check (frames, length, convergence pre-check)
   - Job type: `mmgbsa_production`
   - **Does NOT run MD** — only validates inputs and schedules MD job
5. Job result parser registry (`app/services/job_parsers/`)
6. Tests: `backend/tests/test_compute_wrappers.py`

### Exit Criteria
- [ ] Each wrapper can be instantiated and dry-run (input validation only).
- [ ] Real execution can be triggered via job queue when environment is ready.
- [ ] Parser registry routes outputs to correct parser.

### Scientific Boundaries
- [ ] `MmgbsaReadinessWrapper` blocks if input trajectory < 10 ns or < 200 frames.
- [ ] Pilot/smoke data still cannot populate `official_mm_gbsa_delta_g`.
- [ ] All wrappers log `run_type` explicitly (PILOT vs PRODUCTION).

## P5: Retry Policy + Audit Log

**Duration:** 1 week  
**Goal:** Robust failure recovery and immutable audit trail.

### Deliverables

   - Exponential backoff
   - Per-error-code retry rules
   - Max retry enforcement
2. Failure taxonomy enum + mapping
3. `AuditLogEntry` model + API
4. Audit log write helper (`app/services/audit_log_service.py`)
5. Audit log query endpoint:
   - `GET /api/v1/audit-log?entity_type=&entity_id=&limit=`
6. Tests: `backend/tests/test_retry_policy.py`, `backend/tests/test_audit_log.py`

### Exit Criteria
- [ ] A failed job is retried automatically up to max_retries.
- [ ] Every job state transition is recorded in audit log.
- [ ] Audit log is append-only (no UPDATE/DELETE operations exposed).

## P7: 10–50 ns MD Production Pilot

**Duration:** 2 weeks  
**Goal:** Prepare and guard the first production MD → MM-GBSA pipeline.

### Deliverables
1. Production MD job wrapper (`app/services/md_production_wrapper.py`)
   - Server-only execution
   - Input validation (topology, coordinates, parameters)
   - Progress reporting (ns completed)
2. Production MM-GBSA parser upgrade
   - Reads production `FINAL_RESULTS_MMPBSA.dat`
   - Extracts `official_mm_gbsa_delta_g` ONLY when convergence passed
   - Computes SEM, std, frame count
3. Convergence checker (`app/services/mmgbsa_convergence_checker.py`)
   - Windowed analysis
   - SEM threshold check
   - Returns `CONVERGED`, `PARTIAL_CONVERGENCE`, or `NOT_CONVERGED`
4. Persistence guard update
   - Rejects `official_mm_gbsa_delta_g` if convergence status ≠ CONVERGED/PARTIAL_CONVERGENCE
5. Frontend MM-GBSA Readiness Card update
   - Shows convergence status and SEM
6. Tests: `backend/tests/test_md_production.py`, `backend/tests/test_mmgbsa_convergence.py`

### Exit Criteria
- [ ] A production MD job can be queued (actual simulation run on server, outside dev sprint).
- [ ] Parser correctly extracts official ΔG from production results.
- [ ] Convergence checker correctly classifies results.
- [ ] Guard blocks non-converged data from persistence.

### Scientific Boundaries (Critical)
- [ ] No `official_mm_gbsa_delta_g` without convergence.
- [ ] Pilot ΔTOTAL never written as official ΔG.
- [ ] All three guard layers (parser, guard, frontend) remain active.
