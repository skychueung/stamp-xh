# STAMP v1.2-lab-production Roadmap

**Version:** 1.2-lab-production  
**Goal:** Transition STAMP from a teacher-ready demo into an internal lab-grade computational platform capable of running real batch jobs, managing server-side heavy compute, archiving large files, and integrating with lab informatics systems.  
**Date:** 2026-05-12  
**Branch:** `v1.2-lab-production`

---

## 1. Vision

v1.0 was a **demo**: synthetic data, manual steps, no queue, no server orchestration.  
v1.2 is a **production pilot**: real candidates, real compute, real artifacts, real audit trail.

The platform must support a biologist or computational chemist who:
1. Submits 10–100 candidate peptides.
2. Queues structure prediction (ColabFold), energy analysis (FoldX), docking refinement (FlexPepDock), and binding free energy (MM-GBSA) as **batch jobs**.
3. Monitors job status, retries failures, and downloads artifact bundles.
4. Reviews convergence before accepting any `official_mm_gbsa_delta_g`.
5. Exports validated results to LIMS/ELN.

---

## 2. Production-Grade Modules (9)

### M1. Real Backend Job Queue
Replace the mock/async stubs with a real task queue.
- Queue adapter: Redis + RQ (lightweight, Python-native) or Celery (mature, feature-rich).
- Job lifecycle: PENDING → QUEUED → RUNNING → SUCCEEDED / FAILED / RETRYING / CANCELLED.
- Job status API: real-time polling endpoint.
- Worker process: standalone process consuming queue.

### M2. Multi-Candidate Batch Jobs
Operate on many candidates as a single unit.
- `batch_id` linking multiple `candidate_id`s.
- Pipeline stages per batch: structure → interface → energy → docking → MM-GBSA.
- Partial success support: some candidates succeed, others fail; retry only failed.
- Batch summary: success rate, compute cost estimate, artifact manifest.

### M3. Server Task Scheduler
All heavy compute runs on the lab server (`192.168.31.218`), never on the developer laptop.
- `server_first_for_heavy_compute = true` policy.
- Auto-check server environment: conda/micromamba env presence; create isolated envs if missing.
- Never delete existing environments.
- Local machine only for development, report generation, and UI.

### M4. Batch Compute Management
Standardized job wrappers for each compute step:
- **ColabFold batch:** structure prediction for N candidates.
- **FoldX batch:** AnalyseComplex energy computation.
- **FlexPepDock batch:** peptide-protein docking refinement.
- **MM-GBSA batch readiness:** production-grade binding free energy (10–50 ns MD prerequisite).

Each wrapper:
- Validates input (PDB, sequence, topology).
- Generates job metadata.
- Captures stdout/stderr.
- Parses output into structured JSON.
- Enforces scientific boundaries (e.g., no pilot ΔTOTAL as official ΔG).

### M5. Large File Asset Management
PDBs, trajectories, and logs are too large for SQLite.
- Asset registry table: `asset_id`, `job_id`, `candidate_id`, `file_type`, `path`, `size_bytes`, `sha256`, `storage_backend`.
- Supported file types: PDB, CIF, PDBQT, mdcrd/nc (trajectory), prmtop/inpcrd, log, tar.gz bundle.
- Storage backends: local filesystem (dev), server NFS/SMB (lab), S3-compatible (future).
- Bundle export: tar.gz per batch with manifest.

### M6. Retry and Failure Handling
Robust failure taxonomy and recovery.
- States: PENDING, QUEUED, RUNNING, SUCCEEDED, FAILED, RETRYING, CANCELLED, BLOCKED, PARTIAL_SUCCESS.
- Retry policy: configurable `max_retries`, exponential backoff, retry-only-failed within batch.
- Failure taxonomy: ENV_MISSING, INPUT_INVALID, COMPUTE_TIMEOUT, CONVERGENCE_FAILED, DISK_FULL, SERVER_UNREACHABLE.
- Alerting: log warnings; optional webhook/email on repeated failure.

### M7. Audit Log
Immutable record of every significant action.
- Events: user action, job submit, job cancel, retry, result persist, export, LIMS sync, login/logout, permission denied.
- Schema: `event_id`, `timestamp`, `user_id`, `action`, `entity_type`, `entity_id`, `before_state`, `after_state`, `ip_address`, `session_id`.
- Retention: 90 days hot, archive to compressed JSON after.

### M8. LIMS / ELN Real API Integration
Upgrade from `MOCK_READY` to `REAL_API_READY`.
- Connector config: `base_url`, `auth_mode` (token / OAuth2 / basic), `token_storage_policy`.
- Field mapping: STAMP candidate fields ↔ LIMS sample fields; validation report ↔ ELN experiment record.
- Sync operations: push candidate metadata, push validation report, pull assay results.
- Error handling: retry with backoff, queue for manual review on persistent failure.
- Validation: schema validation before push; checksum on receipt.

### M9. 10–50 ns MD Production Pilot
First real production MD → MM-GBSA pipeline.
- **Server-only**: all production MD runs on `192.168.31.218`.
- **Convergence requirement**: minimum 200 frames, recommended 200–1000 frames.
- **Convergence metrics**: SEM < threshold, std stable across windows.
- **Official ΔG guard**: `official_mm_gbsa_delta_g` may ONLY be set when:
  - `run_type == "PRODUCTION"`
  - `convergence_status == "CONVERGED"` or `"PARTIAL_CONVERGENCE"`
  - `frames_used >= 200`
  - `trajectory_length_ns >= 10`
- **No official ΔG until convergence passed** — three-layer defense (parser, guard, frontend card) remains active.

## 3. Non-Goals (v1.2)

| Item | Reason |
|---|---|
| Cloud deployment (AWS/Azure) | Out of scope; lab intranet only |
| Full GxP compliance | Future phase; v1.2 is pilot |
| Real-time MD visualization | Requires WebGL + large data streaming; deferred |
| Automatic peptide optimization loop | Research feature; deferred to v1.3+ |
| Multi-user RBAC with LDAP | Basic auth + audit log only for v1.2 |

---

## 4. Success Criteria

1. A batch of 10 candidates can be submitted and tracked end-to-end.
2. All heavy compute runs on the lab server.
3. Job failures are retried automatically up to N times.
4. Every action is recorded in the audit log.
5. LIMS/ELN sync succeeds for at least one real API endpoint.
6. A 10 ns production MD pilot completes and passes convergence checks.
7. No fabricated scientific data enters the database.
